1. 系统总览与双模式架构

multiagent-studio 是一个基于 LangGraph + LangChain Agent Middleware 的全栈多智能体协作平台，架构设计深受字节 DeerFlow 启发。系统提供两条核心执行路径：

Single 模式 Lead + SubAgent

Lead Agent 作为主控，通过 ReAct 循环处理用户请求。当遇到需要专业化能力或并行处理的子任务时，Lead Agent 通过 task 工具调用预设或动态创建的 SubAgent。SubAgent 在隔离的事件循环中执行，结果回传给 Lead Agent 汇总。

入口：HarnessService.execute() → build_harness_graph() → create_agent() + 20层中间件

Team 模式 TeamOrchestrator

由 TeamOrchestrator 驱动的多 Agent 团队协作。一个 Lead Agent 负责规划，多个 Member Agent 并行执行。支持 DAG 依赖任务图、负载均衡调度、消息总线通信。

入口：HarnessService._execute_team() → TeamOrchestrator.run()

核心数据流

用户请求 (mode="single" | mode="team")
    │
    ├── mode="single" → HarnessService.execute()
    │   ├── 从 checkpoint 恢复状态
    │   ├── create_agent() + 20 层中间件
    │   ├── astream_events() → SSE 流式输出 (16 种事件类型)
    │   └── SubAgent 并行流 drainer
    │
    └── mode="team" → HarnessService._execute_team()
        └── TeamOrchestrator
            ├── initialize() (加载项目配置 + 成员运行时)
            ├── Phase 1: PLANNING (Lead 拆解任务)
            ├── Phase 2: DISPATCH_LOOP (DAG 调度 + 并行执行)
            └── Phase 3: SYNTHESIS (汇总结果)

2. Agent Team 完整生命周期

2.1 创建阶段

Team 的创建由 HarnessService._execute_team() 触发，当用户请求中 mode="team" 且携带 project_id 时路由到此。

关键文件：harness/main.py L543-635

async def _execute_team(self, thread_id, user_id, message, project_id):
    from harness.team.orchestrator import TeamOrchestrator
    self._active_runs[thread_id] = {"cancelled": False, "mode": "team"}
    orchestrator = TeamOrchestrator(
        project_id=project_id,
        thread_id=thread_id,
        user_id=user_id,
        llm_factory=self._init_llm,
        tool_registry=self.tool_registry,
        subagent_manager=self.subagent_manager,
        skill_storage=self.skill_storage,
    )
    await orchestrator.initialize()
    async for event in orchestrator.run(message):
        yield event

TeamOrchestrator.initialize() 完成以下步骤（harness/team/orchestrator.py L116-207）：

  1. 加载项目配置：从 {data_root}/users/{user_id}/projects/{project_id}.json 读取项目定义
  2. 初始化成员运行时状态：遍历 member_names，加载每个成员的 config.yaml
  3. 构建 TeamContext：包含项目元数据、成员列表、协作规则
  4. 创建 MemberAgentExecutor：加载成员的 SOUL.md 人格文件、解析工具组、创建独立 LLM 实例

2.3 执行流程（三阶段）

Phase 1: PLANNING（规划）

orchestrator.py L236-296

  • 清理上一次运行的残留任务（task_store.clear_all()）
  • 选择 Lead Agent（优先 can_be_lead=True 的成员）
  • Lead Agent 执行规划任务，分析用户目标并拆解为子任务
  • 将用户消息 + 规划摘要作为第一个高优先级任务创建

Phase 2: DISPATCH_LOOP（调度循环）

orchestrator.py L302-370

  • 循环条件：not _is_complete() and not _cancelled
  • 每轮操作：
    1. get_ready_tasks() 获取依赖已满足的待办任务
    2. _select_idle_agent() 分配任务给空闲成员（负载均衡）
    3. asyncio.create_task() 异步执行每个成员任务
    4. 处理消息总线中的未读消息
    5. 从事件队列中取出 SSE 事件并 yield
  • 等待策略：有忙碌成员时 sleep 1s，否则 sleep 0.5s
  • 死锁检测：连续 30 轮空闲且无忙碌成员则判定为死锁

Phase 3: SYNTHESIS（汇总）

orchestrator.py L372-411

  • 收集所有 COMPLETED 和 FAILED 任务
  • 将完成任务的输出汇总为最终结果

2.5 销毁/清理

Team 执行结束后的清理逻辑：

  • 运行期标记移除：self._active_runs.pop(thread_id, None)
  • 取消机制：TeamOrchestrator.cancel() 将所有 busy 成员设为 idle
  • 任务板清理：下次运行开始时通过 clear_all() 清空
  • 消息总线：JSONL 追加方式持久化，不主动清理（保留历史记录）

3. Lead Agent + SubAgent 双层编排

3.1 Lead Agent 的角色

Lead Agent 是一个配置提供者（configuration provider），不包含 run() 方法，实际执行由 create_agent() 内部的 ReAct 循环驱动。

核心职责（harness/agents/lead_agent.py L499-672）：

  • 构建系统提示词：get_system_prompt() 组装 XML 结构化的系统提示词

  • 决策调度：系统提示词中明确指导——只在真正并行工作或需要专业化能力时使用 SubAgent

3.4 ReAct 循环实现

ReAct 循环由 LangChain 的 create_agent() 内部实现，通过 HarnessGraphFactory 封装（harness/graph_factory.py L64-94）：

def build(self) -> Any:
    inner_agent = create_agent(
        model=self.llm,
        tools=self.tools,
        system_prompt=self.system_prompt,
        middleware=self.middlewares,
        state_schema=HarnessState,
    )
    graph = StateGraph(HarnessState)
    graph.add_node("agent", inner_agent)
    graph.set_entry_point("agent")
    graph.add_edge("agent", END)
    return graph.compile(checkpointer=self.checkpointer)

SubAgent 的 ReAct 循环在 SubagentExecutor._aexecute() 中实现（harness/agents/subagent_executor.py L538-672），使用 astream(stream_mode="values") 获取完整状态快照，通过增量检测收集所有消息类型。

5. 边界条件深度分析

5.1 并发控制（四层）

Layer 1: SubagentManager 信号量

asyncio.Semaphore 钳制到 [2, 4]，控制同时执行的 SubAgent 数量。

self._max_concurrent = min(max(int(max_concurrent), 2), 4)
self._semaphore = asyncio.Semaphore(self._max_concurrent)

Layer 2: SubagentLimitMiddleware

在 aafter_model 阶段截断超出限制的 task 工具调用。create_agent 在单批次中执行所有工具调用，因此每轮限制等同于并发限制。

Layer 3: HarnessService 容量限制

_active_runs_max = 1000，超出时拒绝新请求。

Layer 4: Team 调度器负载均衡

_select_idle_agent() 选择已完成任务最少的空闲成员。

5.2 错误处理与恢复

错误类型恢复机制关键参数
LLM 调用失败 指数退避重试 → 注入错误 AIMessage max_retries=3, base_delay 指数增长
工具调用失败 重试 → 返回错误 ToolMessage（不抛异常） max_retries=3
SubAgent 执行失败 try_set_terminal(ERROR) 单写者保护 锁保证 first-writer-wins
Team 任务失败 重置为 PENDING → 重新调度 max_retries=3, retry_delay=2s

SubAgentResult 的单写者终端状态保护（harness/models.py L168-205）：

def try_set_terminal(self, status, *, output=None, error=None, ...) -> bool:
    """Set a terminal status exactly once — first writer wins."""
    with self._state_lock:
        if self.status.is_terminal:
            return False  # 后续写入被静默拒绝
        # ... 设置终态
        return True

5.4 Token 限制与上下文压缩

触发条件（harness/config/summarization_config.py）：

  • trigger：ContextSize 阈值（token 数或消息数），支持 OR 语义多条件
  • keep：压缩后保留的消息数（默认 20 条）
  • trim_tokens_to_summarize：摘要前裁剪的最大 token 数（4000）
  • preserve_dynamic_context_reminders：保留动态上下文提醒不被压缩

关键设计：摘要前触发 memory_flush_hook，将即将被压缩的对话上下文保存到记忆系统，实现"压缩前 flush"。

5.5 HITL 澄清机制

消息驱动的状态管理——不使用自定义状态键，而是直接从消息历史推断挂起状态：

  1. 系统提示词强制：CLARIFY → PLAN → ACT 优先级
  2. 工具调用拦截：ClarificationMiddleware 拦截 ask_clarification，通过 Command(goto=END) 中断 ReAct 循环
  3. 挂起状态检测：get_pending_clarification() 逆序遍历消息推断挂起状态
  4. 恢复执行：respond_to_clarification() 从 checkpoint 恢复，追加用户回答作为 HumanMessage

核心理念："一个搞不定，组队来" — 文件收件箱 + 队友线程。

关键设计

MessageBus（文件收件箱）

每个 Agent 有一个 .jsonl 邮箱。发消息 = 往对方文件 append 一行 JSON。读消息 = 读文件 + 删除（消费式）。

class MessageBus:
    def send(self, from_agent, to_agent, content, msg_type="message"):
        msg = {"from": from_agent, "to": to_agent,
               "content": content, "type": msg_type, "ts": time.time()}
        with open(f".mailboxes/{to_agent}.jsonl", "a") as f:
            f.write(json.dumps(msg) + "\n")

    def read_inbox(self, agent):
        msgs = [json.loads(l) for l in inbox.read_text().splitlines()]
        inbox.unlink()  # 消费式：读完删除
        return msgs

7. 参考资源：s16 Team Protocols

ProtocolState request-response dispatch_message match_response

核心理念："队友之间要有约定" — request-response 模式驱动协商。

解决的两个核心场景

  1. 关机场景：Lead 发请求，队友确认收尾后关机（避免写到一半的文件留在磁盘）
  2. 计划审批场景：队友提交计划，Lead 审批通过后再动手

核心机制

ProtocolState — 请求状态追踪

@dataclass
class ProtocolState:
    request_id: str      # 唯一 ID
    type: str            # "shutdown" | "plan_approval"
    sender: str
    target: str
    status: str          # pending | approved | rejected
    payload: str
    created_at: float

pending_requests: dict[str, ProtocolState] = {}

状态机

          ┌─────────┐
  创建 →  │ pending │
          └────┬────┘
               │
        ┌──────┴──────┐
        ↓             ↓
  ┌──────────┐  ┌──────────┐
  │ approved │  │ rejected │
  └──────────┘  └──────────┘

match_response — 三重防护

  1. 请求不存在 → 跳过
  2. 类型不匹配 → 跳过（防止跨协议误关联）
  3. 已解决 → 跳过重复（幂等性）

关键改进

  • 统一 inbox 消费：consume_lead_inbox() 先路由协议消息再返回内容
  • Idle 等待：队友完成任务后不退出，进入 idle 轮询状态
  • 单一机制，多种协议：一个状态机 + request_id 关联复用于多种协议

8. 参考资源：s17 Autonomous Agents

idle_poll scan_unclaimed claim_task 自组织

核心理念："自己看板，自己认领" — 队友自组织，不依赖 Lead 分配。

三阶段生命周期

阶段行为退出条件
WORKinbox → LLM → 工具循环stop_reason != tool_use
IDLE每 5s 轮询 inbox + 任务板60s 超时

核心函数

idle_poll

IDLE_POLL_INTERVAL = 5   # seconds
IDLE_TIMEOUT = 60         # seconds

def idle_poll(name, messages, role) -> str:
    """Return 'work', 'shutdown', or 'timeout'."""
    for _ in range(IDLE_TIMEOUT // IDLE_POLL_INTERVAL):
        time.sleep(IDLE_POLL_INTERVAL)
        # ① 检查收件箱（优先，可能含 shutdown_request）
        inbox = BUS.read_inbox(name)
        if inbox:
            for msg in inbox:
                if msg.get("type") == "shutdown_request":
                    return "shutdown"
            return "work"
        # ② 扫描任务看板
        unclaimed = scan_unclaimed_tasks()
        if unclaimed:
            claim_task(unclaimed[0]["id"], name)
            return "work"
    return "timeout"

scan_unclaimed_tasks

三个条件：必须是 pending、没有 owner、所有 blockedBy 依赖已完成。

claim_task — owner 检查

检查 task.owner 避免最明显的"后写覆盖"问题。真实 CC 用 proper-lockfile 保护任务文件。

身份重注入

autoCompact 之后，messages 可能被压缩成摘要。每次进入新 WORK 阶段时检查 messages 长度，过短则重新注入身份信息。

真实 CC 的组合路径

CC 的实际实现是四个机制的组合，而非单一轮询：

  • idle_notification：队友完成工作后通知 Lead
  • mailbox 轮询：500ms 循环检查三类来源
  • task watcher：fs.watch() 监听任务目录变化
  • 主动 claim：轮询中也会 tryClaimNextTask()

9.3 关键设计差异

差异 1：调度模式 — Lead-Driven vs Autonomous

multiagent-studio 采用 lead_driven 模式，Lead Agent 负责拆解任务和分配，Orchestrator 通过 _select_idle_agent() 做负载均衡。而 s17 推崇 Autonomous 模式，队友自己扫描任务看板、自己认领。

影响：Lead-Driven 模式下 Lead Agent 是单点和瓶颈，但控制更精确；Autonomous 模式扩展性更好，但需要更复杂的并发控制（文件锁）。

差异 2：协议握手 — 缺失 vs 完整

multiagent-studio 未实现 s16 的 shutdown/plan_approval 协议握手。Team 的取消是通过 orchestrator.cancel() 直接设置标志位，而非通过消息协议与成员协商。这意味着成员可能在执行中间被强制中断。

影响：缺少 graceful shutdown 可能导致资源泄漏（如未关闭的文件、未提交的事务）。

差异 3：任务持久化 — 内存 vs 文件

s17 的任务看板是文件系统（.tasks/task_*.json），队友通过 fs.watch() 监听变化。multiagent-studio 的 TeamTaskStore 也使用文件持久化（fcntl 文件锁），但调度由 Orchestrator 集中管理，成员不主动扫描。

差异 4：隔离深度

multiagent-studio 的 SubAgent 隔离远比 s15 的 daemon 线程重：

  • 独立持久化事件循环（守护线程）
  • 协作式取消（threading.Event + 迭代边界检查）
  • 单写者终端状态保护（锁 + first-writer-wins）
  • 可选的 Git Worktree 文件级隔离
  • ContextVar 跨线程传递
  • 标签过滤的 SSE 事件流

差异 5：中间件覆盖率

s15-s17 每章聚焦一个机制（通信/协议/自治），教学版省略了错误恢复、记忆、技能等。multiagent-studio 有完整的 20 层中间件覆盖所有横切关注点，SubAgent 也有 7-9 层精简中间件。

10. 总结与启示

架构成熟度

multiagent-studio 在工程成熟度上远超 learn-claude-code 的教学版本，体现在：

  • 完整的中间件管线：20 层覆盖错误恢复、安全、记忆、压缩、循环检测等
  • 深度隔离：6 层隔离机制确保 SubAgent 上下文安全
  • 完善的 Watchdog：超时、死锁、循环依赖三层保护
  • 生产级特性：SSE 流式、DAG 依赖、负载均衡、持久化消息总线

可借鉴的设计

从 s16 借鉴：协议握手

当前项目的 cancel() 是强制性的，可借鉴 s16 的 shutdown_request → shutdown_response 握手模式，实现 graceful shutdown，让成员在收到关机请求后完成当前操作的收尾。

从 s17 借鉴：自治能力

当前的 lead_driven 模式下 Lead Agent 是瓶颈。可考虑实现 hybrid 模式（数据模型中已定义但可能未完全实现），让空闲成员主动扫描任务看板认领任务，减轻 Lead Agent 的调度负担。

从 s15 借鉴：权限冒泡

教学版省略了权限冒泡，但真实 CC 有完整的 permission_request → permission_response 机制。当前项目可在 Team 模式中引入类似的权限审批流，让 Member Agent 遇到高风险操作时请求 Lead Agent 审批。

架构演进方向

  1. 实现协议握手：为 Team 成员添加 shutdown/plan_approval 协议，实现 graceful 退出
  2. 支持自治模式：激活 TeamExecutionMode.HYBRID，允许成员主动认领任务
  3. 任务看板监听：引入 fs.watch() 或类似机制，让成员实时感知新任务
  4. 权限冒泡：为 Member Agent 添加权限请求工具，通过消息总线与 Lead Agent 协商
  5. 身份重注入：在上下文压缩后自动重注入成员身份信息（当前 SubAgent 排除了 SummarizationMiddleware）

本报告基于对 multiagent-studio 项目代码库的深度分析和 learn-claude-code s15/s16/s17 章节内容的研读，仅做架构分析，未进行任何代码修改。
