# 定时任务（Cron）系统通俗讲解

> 写给刚接触这个项目的人：不需要任何定时任务、分布式系统的背景，
> 跟着"一个任务的一生"走一遍，就能看懂整个设计。
> 文末附名词小词典和代码位置速查表。

---

## 一、先搞清楚：这个系统是干什么的？

想象你有一家餐厅，提供一种特殊服务：**预定单**。

> "每天早上 9 点，给我送一份早餐。"
> "每 30 分钟，检查一次后厨的煤气有没有异常，有问题打电话告诉我。"

你不用每天打电话来叮嘱，餐厅自己会按时做。这就是 cron 定时任务：
**你设定一个时间表，系统到点自动让 AI Agent 去干活，你甚至不用在线。**

这个"餐厅"由三个角色组成：

```
你（用户）
  │ 用手机下单
  ▼
前端（Next.js, 端口 3000）          ← 餐厅的点单 App
  │
  ▼
App 服务（FastAPI, 端口 8000）      ← 调度室：管预定单的小本子、到点派单、写工作记录
  │ 打电话（SSE 长连接）
  ▼
Harness 服务（LangGraph, 端口 8001） ← 后厨：真正干活的 AI Agent
```

- **调度室（App）**：保存所有预定单（存在数据库里），有个调度员每 15 秒翻一次小本子，看到期的单子就打电话让后厨开工。
- **后厨（Harness）**：接到电话后，AI Agent 开始干活（搜索、写代码、读文件……），干活过程通过"直播电话"实时汇报给调度室。
- **小本子**：就是数据库里的两张表——`scheduled_tasks`（任务定义）和 `task_runs`（每次执行的记录）。

## 二、一个任务的一生（完整流程）

### 阶段 1：出生 —— 任务是怎么被创建的

有两条"下单"通道：

**通道 A：你在 App 上自己填表单**

在"定时任务"页面点"新建"，填三样东西：

1. **叫什么名字**：比如"每日晨报"
2. **干什么活**（prompt）：比如"汇总昨天的邮件，生成一份摘要"
3. **什么时候干**：选"周期任务"（cron 表达式）或"一次性"（定一个具体时间）

填 cron 表达式的时候，页面会**实时显示未来 5 次触发时间**，你不用死记语法——这就是"过程清晰"的设计。

> cron 表达式就是 5 个格子：`分 时 日 月 星期`。
> `0 9 * * *` = 每天 9 点；`*/30 * * * *` = 每 30 分钟。

**通道 B：你对 AI 说一句话，它自己建**

在普通对话里直接说："每天早上 9 点帮我汇总邮件"。AI Agent 会调用一个叫 `cron` 的工具，自己把任务建好。任务卡片上会多一个紫色徽章"**Agent 创建**"，提醒你这是 AI 自己排的活，你可以随时修改或删掉它。

细节保护：你说"10 分钟后提醒我"时，AI 其实并不知道现在几点——所以这类相对时间它不会自己换算，而是直接告诉调度室 `delay="10m"`（相对时长），**由服务器按自己的时钟算出准确时间**，时间永远不会对不上。

两条通道最后殊途同归：往数据库的 `scheduled_tasks` 表写一行记录，其中最关键的字段是 **`next_run_at`（下次执行时间）**。

> **设计要点**：数据库里的这行记录，是整个系统的"唯一事实来源"。
> 系统不靠记性（内存）记时间，全靠这本账。这样做的好处后面会讲。

### 阶段 2：等待 —— 调度员每 15 秒翻一次本子

App 服务启动时，会启动一个后台循环（调度员）：

```
每 15 秒：
    翻翻小本子（查数据库）：
        有没有「已启用」且「next_run_at 已经过了」的任务？
    有 → 进入"认领"环节
    没有 → 继续睡觉
```

**为什么是"每 15 秒翻本子"，而不是"定一个精确的闹钟"？**

因为闹钟存在脑子里，服务器一重启就全忘了；而本子（数据库）永远都在。
重启之后翻开本子就知道下一个任务几点该跑——**重启恢复是免费的**。
而且 cron 表达式最小粒度就是 1 分钟，15 秒看一次足够准。

> 对应代码：`SchedulerService._loop()` 和 `_tick()`
> （`app/services/scheduler.py:119`、`:133`）

### 阶段 3：认领 —— 先盖章，再干活（最重要的一步）

调度员发现"每日晨报"到期了，他**不是直接打电话开工**，而是先做一件事：

> 在本子上把这个任务的 `next_run_at` 改成"明天 9 点"，**改完才打电话**。

为什么顺序这么讲究？想象两个意外：

- **如果先干活再记账**：干到一半服务器断电了。重启后本子上还写着"今天 9 点该跑"→ 任务会**再跑一次**。用户收到两份晨报。
- **先记账再干活**：干到一半断电了。重启后本子上已经是"明天 9 点"→ 不会重跑。最坏情况是这次晨报丢了，但绝不会送两份。

这个原则叫 **at-most-once（最多执行一次）**：宁可丢一次，不可跑两次。
对定时任务来说，"丢一次"通常没事，"重复执行"（重复发邮件、重复下单）才是事故。

盖章动作还有一个防呆设计（术语叫 **CAS 乐观锁**）：

```sql
UPDATE scheduled_tasks
SET next_run_at = 新时间
WHERE id = 任务ID AND next_run_at = 旧时间   -- 关键：带着旧值比对
```

如果将来部署了**两台**调度室服务器，它们同时看到同一个到期任务：
只有第一台能盖章成功（第二台发现"旧时间对不上，被人抢先了"，就放弃）。
**多实例部署也不会重复执行。**

另外，整批到期任务会合并成**一条** UPDATE 盖章（不是逐条盖），
数据库只往返一次——这是应对"整点高峰几千个任务同时到期"的关键手段。

> 对应代码：`_claim_batch()`（`app/services/scheduler.py:198`）

### 阶段 4：过期与迟到 —— 睡过头了怎么办？

调度员也会遇到"本子上一看，这单 3 小时前就该做了"的情况（比如服务器停机维护了）。处理规则（术语叫 **misfire 策略**）：

| 情况 | 规则 | 类比 |
|---|---|---|
| 周期任务，迟到不多（宽限窗口内） | 正常补做一次 | 午睡晚起 10 分钟，该吃还得吃 |
| 周期任务，迟到太久 | **跳过，直接快进到下一个时间点** | 停机 8 小时，"每小时任务"不会补跑 8 次轰炸你 |
| 一次性任务，迟到 ≤ 2 分钟 | 补做 | 闹钟响时没听见，2 分钟内发现还来得及 |
| 一次性任务，迟到 > 2 分钟 | 标记"已跳过"，任务停用 | 飞机起飞了，不追了 |
| 任务设了过期时间且已过期 | 自动停用 | 优惠券到期作废 |

宽限窗口的计算：半个调度周期，但夹在 2 分钟到 2 小时之间。

> 对应代码：`resolve_fire_plan()`（`app/services/cron_utils.py:146`）

### 阶段 5：执行 —— 后厨开工，全程直播

认领成功，调度室拨打"直播电话"给后厨（Harness），AI Agent 开始干活。
这通电话是 **SSE 长连接**——可以理解为"一直保持通话的直播热线"，Agent 每说一句话、每用一次工具，都实时传回来。

调度室一边听直播一边记笔记（把过程写入数据库）：

- Agent 说了什么 → 记成"AI 消息"
- Agent 用了什么工具 → 记成"工具调用记录"
- 干完了 → 把 AI 的完整回答存进一个**会话（Thread）**，你打开就能看到

> 对应代码：`run_scheduled_task()` 和 `_consume_stream()`
> （`app/services/scheduler.py:223`、`:317`）

**执行期间的两条"军规"（安全闸门）**：

因为是无人值守（你不在旁边看着），Agent 的两项能力被临时收走：

1. **不许再造定时任务**。否则可能出现"任务 A 建任务 B，任务 B 建任务 C"的递归失控，账单爆炸。执行时系统会给状态打个 `unattended` 标记，AI 的 `cron` 工具看到这个标记就拒绝工作。
2. **不许向你提问**。平时 Agent 拿不准会问用户（"你要删哪个文件？"），但无人值守时问了没人答，任务会永远卡住。所以提问会被改写成一句提示："现在没人能回答你，请根据已有信息自己拿主意，继续干。"

> 对应代码：闸门 1 在 `harness/tools/builtins/cron_tool.py:123`，
> 闸门 2 在 `harness/middleware/clarification.py:185`

**超时规则：不看总时长，看"是不是还活着"**

初版设计是"最多干 30 分钟，超时就杀"。问题是：有的正经活（比如深度调研）就是要干一两个小时，只要它在持续干活，就不该被杀。

现在改成：**600 秒没有任何动静（一条直播消息都没有）才判定"挂掉了"**。
只要 Agent 还在说话、在用工具，说明活着，就可以一直干（另设 4 小时绝对上限兜底）。

类比：考核保安不是"上班满 8 小时就赶人"，而是"连续 10 分钟没巡逻打卡才叫醒看看"。

> 对应代码：`_consume_stream()` 里的 `anext` 计时循环（`app/services/scheduler.py:365`），
> 配置项 `SCHEDULER_INACTIVITY_TIMEOUT`（默认 600 秒）

### 阶段 6：收尾 —— 写工作报告和小红点通知

干完活，调度室写一条执行记录（`task_runs` 表）：成功还是失败、几点开始几点结束、AI 回答的前 500 字摘要、出错原因。

然后分两种任务：

**普通任务**：在侧边栏"定时任务"入口亮一个**红点数字**，告诉你"有 N 个任务跑完了"。
点进去展开执行历史，红点自动消除（标记为已读）。

**静默任务**（创建时勾选"静默模式"）：适合高频巡检，比如"每 30 分钟检查服务器状态"。
系统会事先跟 Agent 约定好："**没事的话，只回复 `[SILENT]`，别废话。**"

- 如果 Agent 回 `[SILENT]`：会话里**什么都不写**（不然一天 48 条"没事"刷屏），执行记录里留一条"静默完成"供查证，而且**不亮红点**——没事不打扰你。
- 如果真发现问题：正常写会话、正常亮红点提醒你。

> 对应代码：静默判定在 `_consume_stream()`（`app/services/scheduler.py:425`），
> 未读统计在 `unread_count()`（`app/api/scheduled_tasks.py:115`）

### 阶段 7：意外与善后

| 意外 | 系统的处理 |
|---|---|
| 执行到一半服务器重启 | 下次启动时，把卡在"运行中"的记录标记为"已中断"（`_recover_interrupted_runs`，`scheduler.py:104`），任务本身等下个周期再跑 |
| 用户手动关机前的优雅退出 | 停止认领新任务，已在执行的最长等 30 秒（`shutdown`，`scheduler.py:86`） |
| 任务挂了（Harness 连不上/报错） | 记录为失败并展示错误——**失败永远可见**，不会悄悄吞掉 |
| 你点了"立即运行" | 把 `next_run_at` 拨到现在，走正常调度流程，没有任何特殊分支（`trigger_task`，`app/api/scheduled_tasks.py:288`） |

## 三、四个"巧妙小心思"

这些设计单看很小，合起来体现了生产级系统的考虑。

### 1. 抖动（Jitter）：错开用水高峰

全校学生都在早上 9:00 同时打开水龙头，水压会崩。
同理，很多用户的任务都会设"每天 9 点"，如果全部 9:00:00 准点触发，AI 服务会被瞬时打爆。

解决办法：每个任务按自己的 id 算出一个固定延迟（最多推迟周期的 10%，上限 15 分钟）。
有的 9:03 跑，有的 9:11 跑——**每个任务每次偏移都一样**（确定性哈希），所以行为可预测，用户无感知。

> 代码：`jitter_delay_seconds()`（`app/services/cron_utils.py:80`）

### 2. 固定会话 vs 新会话

- **每次新建会话**（默认）：每次执行都是一张白纸，互不污染。
- **固定会话**：所有执行共用一个会话，Agent 记得"上次检查的结果"，适合"跟进昨天的事"这类任务。
  细节保护：如果这个会话此刻正在被你自己使用（正在跑别的），定时触发会**推迟到下一轮**，不跟你抢。

### 3. 上限与兜底

- 每个用户最多 50 个任务（防止失控，Claude Code 也是这个数）
- 单次 tick 最多认领 100 个任务（防止突发打满）
- 最多 20 个任务同时执行（信号量限流）
- 一个任务出问题，绝不影响同批其他任务（逐个 try/except 隔离）

### 4. 坏数据不进库

cron 表达式写错了？创建时就报错拒绝（前端还能实时预览未来触发时间帮你写对）。
万一本子里混进了"周期任务但没有表达式"的异常数据，系统会把它标记为错误并停用——
**显式报错，绝不静默消失**。

## 四、名词小词典

| 名词 | 一句话解释 |
|---|---|
| **cron 表达式** | 描述"什么时候执行"的 5 格公式：分 时 日 月 星期。`0 9 * * *` = 每天 9 点 |
| **SSE** | 服务器向浏览器/调用方单向"直播"数据的 long connection，像一直不挂的电话 |
| **Agent** | 干活的 AI：能思考（调 LLM）、能用工具（搜索/读写文件/执行命令）的循环程序 |
| **ReAct 循环** | Agent 的工作节奏：想一步 → 用工具 → 看结果 → 再想一步……直到完成 |
| **会话 / Thread** | 一段对话的容器，定时任务的结果都存在这里给你回看 |
| **at-most-once** | "最多执行一次"：宁可丢，不重复 |
| **CAS（乐观锁）** | 更新数据库时带上旧值比对，对不上说明被别人抢先，就放弃——防多实例重复执行 |
| **misfire** | 错过了预定时间。策略：窗口内补跑，超窗跳过 |
| **jitter（抖动）** | 给触发时间加个随机小偏移，把并发高峰错开 |
| **中间件（Middleware）** | 套在 Agent 每次 LLM/工具调用外的一层"滤网"，做重试、安全、统计等横切工作 |
| **unattended（无人值守）** | 没有用户在线的执行模式，需要禁用"提问""再建任务"等交互能力 |
| **[SILENT]** | 和 Agent 约定的暗号：回这个就代表"无事可报"，系统就不打扰用户 |
| **幂等** | 同一个操作做 1 次和做 N 次效果一样。防重复执行的终极思路 |

## 六、一图总结

```
创建                     调度                     执行                      收尾
─────                    ─────                    ─────                     ─────
你填表单                  每15s查库                 建/复用会话                写执行记录
 或                      enabled且                调Harness直播             成功→摘要
你对AI说一句              next_run_at过期      →    AI干活,全程汇报      →    失败→错误可见
  │                        │                        静默→丢弃不写            非静默→亮红点
  ▼                        ▼                        提问→改为自己决策          静默→不打扰
DB存一行               先盖章(改next_run_at)        再建任务→拒绝            展开历史→红点消
(next_run_at)          再执行(at-most-once)        600s无动静→判挂起
                       迟到太久→跳过不补跑
```

看懂这张图，就看懂了这个项目的定时任务系统。
