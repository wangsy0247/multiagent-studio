MultiAgent Studio — Agent 引擎后端架构

基于 LangGraph + LangChain 的企业级 AI Agent 编排引擎，覆盖单 Agent ReAct 推理与多 Agent 团队协作双模式，从图编排到沙箱隔离全链路自研

Python 3.12 LangGraph (create_agent + StateGraph) LangChain Agent Middleware FastAPI + Pydantic asyncio + ContextVar PostgreSQL + pgvector Redis Docker Compose

项目背景与内容

01 项目定位

MultiAgent Studio 的后端是一个AI Agent 编排引擎（代号 harness），旨在解决单一 LLM Agent 在复杂任务场景下的能力瓶颈。引擎提供两种执行模式：

  • Single Mode：Lead Agent 驱动 ReAct 循环，可按需派发 SubAgent 在独立线程中并发执行子任务（研究、编码、分析等），通过 asyncio.Semaphore 控制并发度
  • Team Mode NEW：多 Agent 团队协作，TeamOrchestrator 事件驱动编排，支持任务 DAG 依赖解析、自主认领、Agent 间消息通信、Lead 智能汇总

引擎层（harness/）共 151 个 Python 文件、~31.5K 行代码，涵盖 LangGraph 图编排、20 层中间件管线、沙箱隔离、长期记忆、Skill 系统、MCP 协议集成、Team 协作引擎等完整后端能力。上层通过 FastAPI（app/，32 文件 ~2.8K 行）提供 REST API + SSE 流式接口。

04 解决的核心问题
  • 复杂任务分解：单一 Agent 上下文窗口有限，通过 Lead-SubAgent 分层编排和 Team DAG 任务板实现多步骤、多领域协作
  • 并发执行隔离：多个 SubAgent 同时操作文件系统时的数据竞争——通过 Git Worktree 文件级隔离 + asyncio.Lock 串行化合并解决
  • 安全执行环境：AI Agent 执行 shell 命令时的安全风险——虚拟路径沙箱 + 路径穿越检测 + 三级操作审计 + Docker 容器隔离
  • 长期记忆持久化：跨会话上下文记忆——LLM 驱动记忆提取 + 异步 debounce 队列 + file/mem0 双后端存储
  • 多 Agent 协作编排 NEW：任务分配、依赖管理、消息通信与结果汇总——事件驱动 TeamOrchestrator + 结构化协议握手
  • 上下文窗口管理：长对话 Token 溢出——三触发条件自动压缩 + 安全切割点 + 摘要前 flush 到长期记忆

技术亮点（详细）

1 20 层 Agent Middleware 管线 架构设计

设计并实现了 20 层洋葱模型中间件链（AGENT_MIDDLEWARE_ORDER），是整个 Agent 引擎的核心骨架。每个中间件实现 HarnessAgentMiddleware 协议，可选择性覆写 6 种钩子：

  • abefore_agent / aafter_agent：Agent 执行前后的初始化与清理
  • abefore_model / aafter_model：LLM 调用前后的上下文注入与后处理
  • awrap_model_call：LLM 调用包裹器（嵌套执行，类似 Express middleware）
  • awrap_tool_call：工具调用包裹器（安全审计、错误处理、并发限制）

执行规则：before 类钩子按索引 0→19 正向执行，after 类逆向 19→0，wrap 类按声明顺序嵌套（后注册 = 外层 wrapper）。

2 事件驱动多 Agent 团队协作引擎 NEW 核心

实现了完整的多 Agent 团队协作系统（~2000 LOC），核心组件包括：

TeamOrchestrator（编排器，~990 LOC）—— 四阶段事件驱动编排：

  • PLANNING：加载项目 JSON → 解析 Lead 身份 → 生成 AgentCard → 创建 TeammateAgent
  • SPAWN：启动所有 TeammateAgent 的 asyncio Task（每个是独立持久化 Agent）
  • DISPATCH_LOOP：事件循环分配就绪任务 → 负载均衡（completed 少的优先）→ SSE 实时推送
  • SYNTHESIS：Lead LLM 智能汇总（非静态 dump，构建 synthesis_task 让 Lead 综合）

TeammateAgent（持久化 Agent，~975 LOC）—— 状态机驱动：

SPAWNING → IDLE ↔ WORKING → SHUTTING_DOWN → SHUTDOWN/FAILED

# IDLE 状态：asyncio.Event 事件驱动等待（非 sleep 轮询）
#   - 等待新任务分配 / inbox 消息 / shutdown 请求
# WORKING 状态：create_agent() 构建 ReAct agent + astream_events(v2) 推送 SSE
#   - LangGraph checkpointer 跨 run 持久化状态
#   - _inject_identity() 防止长上下文后遗忘身份

自主认领机制（三级优先级）：

  • P1 强制分配：assigned_agent == self → 直接认领
  • P2 饥饿预防：等待 > 2min 且无 owner → 认领
  • P3 领域匹配：match_score >= 25.0 → 认领（工具 +25/个、技能 +30/个、关键词 Jaccard +2/个）

Watchdog 机制：整体超时 30min / 死锁检测 2min 无活动 / DFS 三色标记法循环依赖检测。

3 DAG 任务板 + 消息总线 NEW

TeamTaskStore（DAG 任务板）：

  • 存储：JSON 文件 + fcntl.flock 文件锁 + 内存缓存 + mtime 校验
  • get_ready_tasks()：返回所有 dependencies 状态为 COMPLETED 的任务
  • get_unclaimed_tasks()：PENDING + assigned_agent=None + 依赖满足
  • check_circular_dependency()：DFS 三色标记法（白/灰/黑）检测循环依赖
  • atomic_update()：读-改-写原子操作，避免并发竞态
  • 任务状态机：pending → in_progress → completed / failed / cancelled

TeamMessageBus（消息总线）：

  • 存储：per-agent JSONL inbox（messages/inbox/{agent_name}.jsonl）
  • drain-on-read：读完即清空，天然无竞态
  • asyncio.Event 实时通知：点对点写入收件人 inbox + Event 触发
  • wait_for_message()：事件驱动等待（Event + timeout），非轮询
  • check_message_loop()：检测 A↔B 乒乓消息（最近 4 条发送者模式）
  • 7 种消息类型：TEXT / BROADCAST / LIFECYCLE / SHUTDOWN_REQUEST / SHUTDOWN_RESPONSE / PLAN_APPROVAL_REQUEST / PLAN_APPROVAL_RESPONSE

结构化协议消息：

  • shutdown 握手：Lead 发送 shutdown_request → Member LLM 决策是否可关闭 → 返回 shutdown_response (approved/rejected)
  • plan_approval：Member 发送 plan_approval_request（带计划内容）→ Lead 审批 → plan_approval_response (approved/rejected)

5 SubAgent 守护线程隔离执行引擎 并发设计

设计并实现了 SubAgentExecutor——在独立守护线程 + 持久事件循环中运行 SubAgent，与父 HTTP 请求生命周期完全解耦：

  • 持久化事件循环：模块级单例 _isolated_loop 运行在 daemon thread 中，即使父请求取消或超时，SubAgent 仍可优雅完成或被合作式取消
  • 合作式取消：使用 threading.Event 在每次 astream 迭代边界检查——从不使用 Future.cancel()（避免资源泄漏和半完成状态）
  • 跨线程消息桥接：通过 asyncio.Queue + run_coroutine_threadsafe() 将 SubAgent 消息从 daemon thread 推送到主事件循环，实现实时 SSE 流式
  • Token 收集：SubagentTokenCollector 回调替代重量级 TokenUsageMiddleware，轻量收集 SubAgent Token 消耗
  • 全量消息收集：astream(stream_mode="values") + 增量消息检测，收集 所有消息类型（AIMessage + ToolMessage），而非仅最后一条
  • ContextVar 传播：copy_context() 将主线程的 ContextVar（沙箱、用户凭证等）复制到 daemon thread
# 核心执行流程
async def _run_subagent(self, config, ...):
    agent = create_agent(llm, tools, middlewares, system_prompt, checkpointer=...)
    async for event in agent.astream_events(input, version="v2"):
        if self._cancel_event.is_set():  # 合作式取消检查
            break
        await self._push_to_stream(event)  # 跨线程桥接

7 SubAgent Git Worktree 文件隔离 并发安全

当多个 SubAgent 并发操作文件时，通过 Git Worktree 实现文件级隔离与合并：

  • 创建：git worktree add 在 .worktrees/{name}_{uuid}/ 创建独立工作目录，分支 subagent/{name}/{uid}
  • 依赖共享：symlink .venv / node_modules（避免重复下载），copy .env / config.local.yaml
  • 合并：asyncio.Lock 串行化合并，git merge --no-ff 合并回主分支；冲突时保留 worktree 供人工检查
  • 清理：合并成功后删除 worktree + 分支；启动时 cleanup_stale() 清理崩溃残留
  • 并发控制：asyncio.Semaphore 限制 [2, 4] 个 SubAgent 同时执行
# Worktree 生命周期
GitWorktreeManager.create(name, base_path)
  → git worktree add .worktrees/{name}_{uuid} -b subagent/{name}/{uid}
  → symlink .venv, node_modules (共享依赖)
  → copy .env, config.local.yaml (隔离配置)

# SubAgent 在 worktree 内操作文件 → 完成后合并
GitWorktreeManager.merge(name, worktree_path)
  → asyncio.Lock() 串行化
  → git merge --no-ff subagent/{name}/{uid}
  → 冲突则保留 worktree 供人工检查
8 LLM 驱动长期记忆系统

设计了异步 debounce 队列 + 双后端存储的长期记忆系统，对齐字节 DeerFlow 架构：

  • 双后端：file（JSON 文件，DeerFlow schema）+ mem0（pgvector 向量数据库，语义搜索）
  • 异步 debounce 队列：以 (thread_id, user_id, agent_name) 为 key 合并多次更新，默认 30s debounce 后批量处理
  • LLM 驱动更新：调用轻量模型分析对话 → 提取记忆 delta → _apply_updates() 合并（user/history summaries 更新 + facts 增删）
  • 置信度过滤：facts 按置信度排序（默认阈值 0.7），去重（casefold），max_facts 截断（默认 100）
  • 摘要前 flush：summarization_hook 在上下文压缩丢弃老消息前，先把它们写入长期记忆
  • 注入策略：首次对话注入完整记忆；同天不重复注入；跨天只更新日期。Token 预算按优先级填充（User Context > History > Facts）

Agent Team 短期记忆 NEW：Team 模式下每个 TeammateAgent 拥有独立的 LangGraph checkpointer，跨 run 持久化执行状态。

9 上下文自动压缩与安全切割

SummarizationMiddleware 在每次 LLM 调用前检查上下文是否需要压缩：

  • 三触发条件（OR 语义）：消息数 ≥ N / 估算 Token ≥ N / 达到模型最大输入的 x%
  • 安全切割：_find_safe_cutoff_point() 确保切割点不在 ToolMessage 上——如果落在 ToolMessage，向前回溯到对应的 AIMessage（含匹配的 tool_calls），保留完整的 AI/Tool 对
  • Dynamic Context 保护：记忆注入的 <system-reminder> 从"待压缩"移到"保留"队列最前面，防止关键上下文丢失
  • 摘要前 flush：_fire_hooks() 触发 memory_flush_hook，将待压缩消息写入长期记忆后再丢弃
  • 原子替换：RemoveMessage(REMOVE_ALL_MESSAGES) → 添加摘要消息 → 添加保留消息，LangGraph reducer 保证原子性

  • SubAgent 跨线程桥接：run_coroutine_threadsafe() 将 daemon thread 中的事件推送到主事件循环的 asyncio.Queue，SSE handler 从 Queue 消费

11 三层配置合并系统 NEW

设计了 L0/L1/L2 三层配置合并机制，支持 per-user、per-agent 的精细化配置：

L0: SYSTEM_DEFAULTS (代码内置默认值, 支持 $VAR 环境变量替换)
       ↓ _deep_merge()
L1: 用户全局 config.yaml  ({data_root}/users/{user_id}/config.yaml)
       ↓ _deep_merge() + _merge_agent()
L2: Per-Agent config.yaml  ({data_root}/users/{user_id}/agents/{name}/config.yaml)
       ↓ + SOUL.md (agent 人格定义)
    → EffectiveConfig (最终生效配置)
  • _interpolate_env()：递归替换 $VAR / ${VAR} / ${VAR:-default}
  • _merge_agent()：tool_groups 和 skills 使用集合 union（扩展），其他 section 替换
  • 热加载：ConfigManager 3 秒 mtime 轮询，变更后触发 on_change 回调
  • create_user_configs()：新用户注册时自动创建全局配置 + default agent

GraphContext 缓存：main.py 以 (user_id, agent_name) 为 key 缓存编译后的 GraphContext（含 EffectiveConfig、LLM、middlewares、compiled graph、LeadAgent），配置变更时失效重编译。

  • 渐进式加载：DeferredToolFilterMiddleware（第 15 层）按需过滤，避免工具列表过长导致 LLM 注意力分散

MCP 协议集成（extensions_config.json）：

  • 支持 stdio / SSE 双传输模式
  • 持久化 session pool：连接复用，避免每次请求重新建立 MCP session
  • OAuth 认证支持 + Cache with mtime invalidation
  • 延迟工具过滤：按 Agent 能力动态过滤可用 MCP 工具
