## mem0 原理分析与接入可行性评估

### 完成内容
- 搜索分析了 mem0（arXiv:2504.19413）的架构原理：LLM 驱动的记忆管理引擎，七步 add() 流水线（消息→事实提取→向量检索旧记忆Top5→LLM判断ADD/UPDATE/DELETE/NONE→并发执行→图存储）
- 深入分析了项目现有记忆系统：FileMemoryStorage（JSON文件）+ MemoryUpdateQueue（debounce 120s）+ MemoryUpdater（LLM驱动）+ DynamicContextMiddleware（注入）+ MemoryMiddleware（入队）
- 识别现有系统 5 个关键缺陷：无向量检索、无主动查询工具、fcntl跨平台问题（Windows报错）、facts≤100上限、Redis/pgvector配置但未用
- 评估接入可行性：高度可行，技术栈兼容（Python+LangChain），架构契合（user_id/agent_id/run_id ↔ user_id/agent_name/thread_id），项目已有 MemoryStorage ABC 可扩展
- 设计渐进式替换方案：保留中间件框架，新增 Mem0Storage 适配器替换 FileMemoryStorage，简化 MemoryUpdater，新增 memory_search 工具，改动量约 300 行

### 产出文件
- `docs/mem0-analysis.md` — 完整分析报告（mem0原理 + 项目现状 + 可行性评估 + 集成方案 + 改造清单）

### 关键结论
- mem0 可解决现有系统全部高严重度问题（向量检索、跨平台、主动查询、无上限）
- 推荐路径：本地Qdrant验证 → Mem0Storage适配器 → pgvector替代 → 数据迁移 → 可选图记忆
- 可复用项目已有的 pgvector Docker 镜像和 Qwen3/DeepSeek 模型

## GBrain vs mem0 对比分析

### 完成内容
- 搜索分析了 GBrain（Garry Tan 开源，YC总裁）：三层架构（Brain Repo Markdown + Retrieval Index PG/pgvector + Knowledge Graph），Compiled Truth+Timeline 双层记忆模型，正则抽取实体关系（0 LLM），Dream Cycle 夜间巩固，30+ MCP 工具
- 对比 mem0 与 GBrain 的 12 个维度：语言栈、集成复杂度、运维负担、改造成本、Windows支持、检索深度、记忆模型、人类可读性、知识图谱、LLM成本、时间处理、生产成熟度
- 评估结论：mem0 胜 6 项（契合度/运维/成本），GBrain 胜 5 项（能力深度），平手 1 项

### 产出文件
- `docs/gbrain-vs-mem0-comparison.md` — 完整对比报告

### 关键结论
- **推荐 mem0**：对本项目而言，集成契合度（Python SDK vs MCP服务）和运维成本（向量库 vs PG+Git+cron）是决定性因素
- GBrain 能力更强（图遍历/合成答案/缺口分析/Markdown可读），但架构重、跨语言、运维复杂
- 最佳实践：借鉴 GBrain 设计思想（Compiled Truth+Timeline / 正则抽关系 / 缺口分析），用 mem0 实现

## mem0 接入方案可行性分析（用户定制方案）

### 用户方案要点
- Chroma 向量库 + 中间件集成 + 组合检索（固定查询+首条消息）+ 相似度判断重查 + user_id/agent_id 过滤 + 时间感知 + MemoryMiddleware 写入

### 分析结论
- 整体可行，总改动量约 380 行
- 三个重难点：① 上下文重组装（messages append-only，不能替换旧 reminder，只能追加）② embedding 延迟（每轮调 API）③ 阈值调参
- 最大的架构冲突：现有 DynamicContextMiddleware 是"首回合注入后冻结"，用户方案要求"话题切换时重查并重组装"，需改为追加新 reminder + prompt 引导
- 推荐分 5 Phase 实施：基础接入 → 组合查询 → 相似度重查 → 时间感知 → 数据迁移

- `docs/mem0-integration-feasibility.md` — 完整可行性分析报告
